# Development Plan

## Goal

Make every demo visitor see the same fixed 30-item showcase inventory
with internally consistent prices: each demo item gets a deterministic
synthetic price series, its current price is the last point of that
series, and the demo portfolio history is the sum of those same item
series. Demo data stays in memory — no synthetic `PriceLog` or
`InventoryValueLog` rows — and real current item prices are used only as
the anchor for their generated series.

## Expected Behavior

### Fixed showcase inventory

- A new `app_fetcher/config/demo_inventory.yml` lists exactly 30
  `market_hash_name` + `base_price_cents` pairs.
- The showcase is identical for every demo session; the token’s `seed`
  remains for auth/traceability but no longer selects items or history.
- Every showcase name exists in `config/demo_items.yml`; the pool keeps
  its 48 curated entries and is still used for metadata (rarity,
  category, icon URL) and for `demo:seed_items`.
- The showcase covers all eight Steam Type categories and a mix of cheap
  skins, mid-tier skins, knives, and gloves.

### Demo item construction

- `Demo::Dataset` builds the 30 demo `Item` objects in memory:
  - metadata comes from the matching `demo_items.yml` entry via
    `ItemParser` (never from the live `Item` row), so missing metadata
    or an unseeded catalog cannot change the demo;
  - the price anchor is the real `Item#current_price_cents` when that
    row exists, is marketable, has a price, and is not
    `price_unavailable`;
  - otherwise the anchor is the entry’s `base_price_cents` from
    `demo_inventory.yml`;
  - the in-memory item receives the anchor as `current_price_cents`, the
    synthetic 24h change, and a generated `price_updated_at`.
- No `Item`, `PriceLog`, `UserInventory`, `UserInventoryItem`, or
  `InventoryValueLog` row is written by demo reads.

### Synthetic price series

- A new `Demo::PriceSeries` collaborator generates a deterministic series
  per `market_hash_name` from a stable digest of the name.
- The series always ends at the item’s anchor price, so the current price
  and the newest history point never jump.
- Supported windows:
  - `24h` → 24 hourly points ending now;
  - `7d` → the last 7 daily points;
  - `30d` → the last 30 daily points;
  - `1y` / `all` → the full 365 daily points.
- Daily points are dated at noon UTC, ordered oldest → newest. Prices
  stay positive and are clamped to a reasonable band around the anchor
  so no item’s history goes absurd.
- Each point carries deterministic `volume`.
- The 7-day trend is five points sampled from the last seven daily
  points, ending at the current price.

### Consistent current values

- `current_price_cents` = the last series point.
- `change_24h_cents` = current price − yesterday’s daily point.
- `change_24h_percent` is derived from those two values by the existing
  serializer.
- `price_updated_at` is generated (for example, `Time.current`) and is
  not read from the real item row.

### Consistent portfolio history

- `Demo::Dataset#value(period:)` computes every portfolio point as the
  sum of all 30 item series at that date.
- The snapshot total is the last portfolio point; `items_count`,
  `pricable_items_count`, and `priced_items_count` are all 30 and
  `complete?` is true.
- `oldest_price_at` is the first generated daily point.
- The portfolio delta is current − previous point in the requested
  window, with `partial: false` and `available: true`.
- The demo summary uses the same snapshot/delta as the portfolio value,
  so the demo card and the `/demo/inventory` hero agree.

### Demo detail and item endpoints

- `GET /api/demo/inventories` returns the fixed 30 in-memory items.
- `GET /api/demo/inventory_summary` returns one summary whose values
  come from the generated snapshot/history.
- `GET /api/demo/inventory_detail?period=&sort=&page=&per_page=`:
  - parses `period` through `Options::DateRange::Param` with the demo
    error class;
  - sorts in memory using `Options::ItemSortOption` semantics
    (`change_24h_desc`, `price_desc`, `price_asc`, `name_asc`) and the
    existing `Appliers::Pagination` bounds;
  - returns trends generated by `Demo::PriceSeries`;
  - returns the priciest item and average item value from the in-memory
    prices;
  - keeps the existing `InventoryDetailSerializer` payload shape.
- `GET /api/demo/inventory_values?period=` returns the summed generated
  portfolio history.
- `GET /api/demo/item_prices/dynamics` returns generated current
  prices/changes for the fixed item set.
- `GET /api/demo/item_prices/trend` returns the generated five-point
  trends.
- `GET /api/demo/item_prices/:market_hash_name/history?period=` returns
  the generated series for a showcase item; an unknown name returns
  `404 { message: "Not found" }`.
- Missing/malformed/expired/wrong-audience tokens and unsupported
  `period`/`sort` values keep their existing `401`/`400` behavior.

### Unchanged

- `Api::Demo::` auth, token claims, error shapes, routes, and CORS.
- All response shapes consumed by the existing React islands.
- `app_core` demo session/cookie/JWT behavior and all UI code.
- Public `Api::Public::`, player `Api::V1::`, and `Api::Admin::`
  behavior.
- The 48-entry `demo_items.yml` pool and `demo:seed_items`.
- No migrations, new gems, or environment variables.

## Implementation Approach

Keep the demo API read-only and keep reusing the existing serializers.
Move the synthetic-data responsibility into two small read collaborators
under `app/queries/demo/`, then let `Demo::Dataset` assemble the existing
query structs from them.

- `Demo::Inventory` loads `config/demo_inventory.yml` into typed entries
  (`market_hash_name`, `base_price_cents`). It does not query the DB.
- `Demo::PriceSeries` owns deterministic generation for one item. It
  takes the name and anchor price, generates daily/hourly series, and
  exposes the window/trend slices. It does not know about the dataset or
  HTTP params.
- `Demo::Dataset` combines `Demo::ItemPool` metadata, real item prices
  (anchor lookup only), and `Demo::PriceSeries` into in-memory `Item`
  objects. It derives the portfolio series by summing item series, then
  builds the existing `InventorySummary`, `InventoryValue`, and
  `InventoryDetails` structs.
- Demo controllers stop calling the real price caches/history query and
  read only from `Demo::Dataset`.
- Sorting moves to Ruby because the prices exist only in memory. The sort
  option enum and pagination bounds stay the same, so the accepted query
  params and error behavior do not change.

## Risks

- **Anchor flapping within a session.** A real price update changes the
  anchor and therefore the whole generated series. It stays continuous,
  but the demo chart can shift mid-session. Accepted; the alternative is
  frozen YAML-only prices.
- **Missing real Item rows.** The fixed dataset still needs metadata from
  `demo_items.yml`; a missing pool entry or malformed YAML breaks the
  dataset. Cover the inventory↔pool contract in specs and fail loudly
  rather than silently falling back to random catalog items.
- **In-memory Item typing.** Serializers expect `Item`; build unsaved
  `Item` objects with string-keyed metadata so `store_accessor` works
  before persistence. Do not save them.
- **In-memory sorting.** `Appliers::SortApplier` cannot sort synthetic
  prices in SQL. Mirror the four `Options::ItemSortOption` semantics in
  Ruby and test all four; keep the same default and error behavior.
- **Time-based drift.** Daily points are anchored to the current date, so
  the same showcase shifts by a day over time. This is expected; the
  dataset is fixed in composition and current values, not frozen
  historical dates.
- **Ranges.** `24h` uses hourly points while portfolio ranges are daily;
  keep the item-history endpoint’s allowed ranges and the portfolio’s
  allowed ranges exactly as they are today.
- **Duplicate/omitted showcase names.** A duplicate changes the portfolio
  count; a name not in the pool raises at read time. Both are caught by
  the inventory/pool contract specs.
- **ADR mismatch.** The current ADR explicitly requires real demo
  prices/history and seed-based selection; leaving it unamended would
  make the implementation contradict documented architecture.

## Assumptions

- “Fixed dataset” means the same 30-item composition and base fallback
  prices for every demo; real current prices may still move the anchor
  (as chosen) without breaking continuity.
- The showcase is a subset of the existing 48-item pool; no new item
  names or icon curation are needed.
- 30 items is the intended demo inventory size; the old 20-item cap is
  retired.
- Synthetic prices are acceptable for demo mode; real `PriceLog` history
  is not required and must not be polluted.
- Generating on read is preferred to pre-seeding demo price logs; no
  separate demo tables or Redis cache are needed.
- The demo token keeps its `seed` claim for compatibility, even though
  the dataset no longer varies by seed.
- Response shapes stay unchanged, so no `app_core`/React changes are
  required.
